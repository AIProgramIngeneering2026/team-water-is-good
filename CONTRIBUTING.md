# Правила командной разработки

## Главное правило

**Изменения попадают в `main` только через Pull Request, одобренный ревьюером.**

- Прямые коммиты и push в `main` запрещены, `--force` тоже.
- Рекомендуется включить защиту ветки `main` на GitHub (Settings → Branches): *Require a pull request before merging* и *Require approvals* (минимум 1).

## Ветки

Каждая задача — в отдельной ветке от актуальной `main`.

Формат: `<тип>/<номер-задачи>-<краткое-описание>`, латиницей, через дефис.

Типы: `feature` (новая функциональность), `fix` (исправление ошибки), `docs` (документация), `refactor` (рефакторинг), `test` (тесты), `chore` (конфигурация и прочее).

Примеры: `feature/12-pdf-text-extract`, `fix/25-empty-file-crash`, `docs/7-contributing`.

После слияния ветка удаляется.

## Коммиты

Формат заголовка: `<тип>(<область>): <описание>`, область необязательна.

- типы те же, что и у веток;
- описание — в повелительном наклонении, до 72 символов, без точки в конце;
- один коммит — одно логическое изменение;
- не коммитим секреты и `.env`-файлы.

Примеры:

```
feature(upload): add PDF and TXT validation
fix(parser): handle PDF without text layer
docs: add CONTRIBUTING.md
```

## Pull Request

1. Обновите `main` и создайте ветку: `git checkout main && git pull && git checkout -b <имя-ветки>`.
2. Работайте небольшими коммитами.
3. Перед PR подтяните свежую `main`, разрешите конфликты, запустите тесты.
4. Отправьте ветку (`git push -u origin <имя-ветки>`) и создайте PR в `main`.
5. В описании PR укажите: что сделано, как проверить, ссылку на задачу (`Closes #12`).
6. Назначьте ревьюера. Незавершённую работу оформляйте как Draft PR.
7. Замечания исправляйте новыми коммитами в ту же ветку.
8. После Approve автор вливает PR (*Squash and merge*) и удаляет ветку.

Один PR — одно логически связанное изменение.

## Code Review

- **Кто проводит:** любой участник команды, кроме автора PR. Нужен минимум один ревьюер.
- **Сроки:** ревьюер откликается в течение 3 рабочих дней, автор отвечает на замечания в течение 3 рабочих дней.
- **Что проверяет ревьюер:**
  - решает ли PR свою задачу;
  - корректность логики и обработку ошибок;
  - читаемость кода;
  - наличие тестов;
  - отсутствие секретов и лишнего кода.
- **Решение** выносится через GitHub Review: *Approve*, *Request changes* или *Comment*.
- Слияние возможно только после минимум одного Approve и устранения обязательных замечаний. Автор не одобряет свой PR.

## Definition of Done

Задача готова, когда:

- [ ] функциональность реализована и соответствует описанию задачи;
- [ ] тесты написаны и проходят;
- [ ] в коде нет отладочного вывода и секретов;
- [ ] документация обновлена, если изменилось поведение;
- [ ] PR создан, описание заполнено, ссылка на задачу есть;
- [ ] Code Review пройдено, получен Approve;
- [ ] PR влит в `main`, ветка удалена.
