# Практика 3. Доменное ядро

**Срок:** воскресенье, 22 ноября, 23:59 (по Екатеринбургу). **Баллы:** 4 личных + 4 командных (см. [ПРАВИЛА.md](../ПРАВИЛА.md)).

На этой неделе — первый код проекта: ядро, которое выполняет задание. Без HTTP и без базы данных — они появятся
на практике 4. На паре вы ломали чужие таблицы переходов ([Взлом Job](p3_job/README.md)); теперь ваш Job
должен выдержать те же злодейства.

## Каждому

**Личное участие — по обычному правилу:** ваш влитой PR или содержательное review в рамках этой практики,
по ссылкам в разделе «Вклад участников» отчёта команды.

**С этой практики — перекрёстное review.** Кого проверяет ваша команда — в [tasks/review_p3.md](review_p3.md).
Каждый участник делает содержательное review хотя бы одного PR проверяемой команды за эту неделю и ставит ссылку
на него в своей строке «Вклада участников». Прав в чужом репозитории не нужно: review — комментариями, лучше к строкам кода.
Такое review тоже засчитывается как личное участие. Подробно — [ПРАВИЛА.md](../ПРАВИЛА.md), раздел о review.

## Команде — в своём репозитории `team-<команда>`

Всё через PR. Поделите пункты между участниками: Job, Registry, Dispatcher и Tool хорошо делятся.

1. **Job с проверкой переходов** — по вашей диаграмме состояний из практики 2. Недопустимый переход **отклоняется
   явной ошибкой**, а не игнорируется молча. Правило живёт в Job, а не в вызывающем коде.
2. **Registry** — по имени операции выдаёт Tool. Неизвестная операция — ошибка «неизвестная операция»
   (код — ваш, например `unknown_operation`).
3. **Dispatcher** — берёт Tool из Registry, ведёт Job по состояниям, превращает ответ Tool — и его падение — в переход Job.
   Конкретных Tool Dispatcher не знает: новый Tool добавляется **без правки Dispatcher**.
4. **Не меньше двух Tool** за контрактом Tool из практики 2. Неверные параметры — ошибка «неверные параметры»
   с указанием поля. Кто проверяет параметры — Tool или вызывающий, — так, как записано в вашем контракте.
5. **Ядро не зависит от фреймворка и БД.** В коде Job, Registry, Dispatcher и Tool нет импортов веб-фреймворка
   и драйвера базы данных. Если ядру нужно хранение — через интерфейс; сейчас достаточно реализации в памяти.
6. **Первые тесты**, запуск одной командой — она записана в README:
    - обычный путь Job — от создания до успешного завершения;
    - **каждое злодейство с пары, применимое к вашему Job**, — отдельный тест, ядро его отклоняет
      ([злодейства З1–З6](p3_job/README.md#злодейства));
    - неизвестная операция и неверные параметры.

   Злодейство неприменимо — например, у вас нет отмены, значит, нет и З3, — объясните это одной строкой в отчёте.

**Рекомендуем, не обязательно:** дайте модели код вашего Job и список злодейств и попросите сыграть атакующего —
найти цепочку команд, которую ядро пропускает. Нашла — добавьте тест и исправьте. Если делали — коротко напишите
в отчёте, что нашла.

## Команде — в `Zadania`

Отчёт — `teams/<команда>/p3.md` по шаблону [templates/p3.md](../templates/p3.md), один PR от любого участника.
В разделе «Вклад участников» — ссылки на PR и review каждого участника, включая перекрёстное review.
PR из этого отчёта повторно в следующих практиках не засчитываются.

## Чек-лист командной оценки

- [ ] Job отклоняет недопустимые переходы явной ошибкой
- [ ] Registry выдаёт Tool по имени; неизвестная операция — ошибка
- [ ] Dispatcher не знает конкретных Tool; падение Tool переводит Job в ошибку
- [ ] Не меньше двух Tool за общим контрактом; неверные параметры — ошибка с указанием поля
- [ ] Ядро не зависит от веб-фреймворка и БД
- [ ] Тесты: обычный путь, все применимые злодейства, две ошибки; запуск одной командой
