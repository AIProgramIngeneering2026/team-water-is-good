# ADR-0001: Локальные Tool в одном процессе

- Дата: 2026-11-15
- Статус: принято

## Контекст и ограничения

NVKDrive использует путь обработки команд:

`HTTP API → Dispatcher → Registry → Tool`

Проект находится на стадии MVP и разрабатывается небольшой командой. Основные операции связаны общими транзакциями PostgreSQL: бронирование места одновременно изменяет поездку, создаёт бронь и обновляет состояние `BookingJob`.

Для проекта важны:

- простой локальный запуск;
- атомарные транзакции;
- единый способ обработки команд;
- возможность тестировать Tool отдельно;
- отсутствие необходимости независимо масштабировать отдельные операции.

## Решение

Все Tool выполняются локально в одном процессе ASP.NET Core.

Dispatcher получает реализацию Tool из Registry и вызывает её через единый контракт. Tool не являются отдельными сетевыми сервисами и взаимодействуют с общим слоем хранения.

В первой версии используются:

- `TripTool`;
- `BookingTool`;
- `TripCompletionTool`;
- `TripCancellationTool`.

Каждый Tool отвечает за собственные бизнес-операции и возвращает результат или ошибку в едином формате.

## Рассмотренные альтернативы

### Отдельный сервис для каждого Tool

Преимущества:

- независимое развёртывание;
- независимое масштабирование;
- изоляция сбоев.

Недостатки:

- сетевые вызовы между компонентами;
- необходимость распределённых транзакций;
- более сложные развёртывание, наблюдаемость и тестирование;
- избыточность для учебного MVP.

Альтернатива отклонена из-за сложности и отсутствия требований к независимому масштабированию.

### Прямые вызовы сервисов без Dispatcher и Registry

Преимущества:

- меньше инфраструктурного кода;
- проще начальная реализация.

Недостатки:

- HTTP API зависит от конкретных обработчиков;
- отсутствует единая точка выбора и запуска Tool;
- сложнее добавлять новые команды и тестовые реализации.

Альтернатива отклонена, поскольку по условиям проекта требуется единый контракт Tool и маршрутизация через Dispatcher и Registry.

## Цена решения

- все Tool масштабируются и развёртываются вместе;
- сбой процесса может затронуть все операции;
- Registry и Dispatcher добавляют инфраструктурный код;
- границы между Tool необходимо соблюдать внутри одного приложения;
- в будущем выделение Tool в отдельные сервисы потребует изменения способа их вызова.

## Условия пересмотра

Решение следует пересмотреть, если:

- отдельные Tool потребуют независимого масштабирования;
- разные части системы будут развёртываться независимо;
- появятся разные требования к доступности Tool;
- одной базе данных станет недостаточно;
- операции потребуют изоляции по безопасности или ресурсам;
- над отдельными Tool начнут работать независимые команды.
