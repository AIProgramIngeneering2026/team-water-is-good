# Требования к NVKDrive

## Термины

- **Поездка** — опубликованное водителем предложение совместной поездки между двумя точками.
- **Бронь** — резерв одного или нескольких мест пассажиром в поездке.
- **BookingJob** — единица работы системы, создаваемая при обработке запроса на бронирование.
- **Активная поездка** — поездка, которую водитель ещё не отменил и не завершил.

## Сценарий 1. Создание поездки

**Цель:** водитель публикует поездку, чтобы пассажиры могли забронировать в ней места.

**Участник:** авторизованный пользователь в роли водителя.

**Основной поток:**

1. Водитель открывает форму создания поездки.
2. Водитель выбирает точки отправления и назначения через API Яндекс Карт.
3. Водитель указывает количество свободных мест, цену одного места и время отправления, время прибытия либо оба значения.
4. Водитель отправляет форму.
5. Сервис проверяет данные, сохраняет активную поездку и показывает её водителю.

**Критерии приёмки:**

- **Дано** водитель авторизован и выбрал две разные точки, **когда** он указывает положительное количество мест, неотрицательную цену и хотя бы одно время, **тогда** сервис создаёт активную поездку.
- **Дано** водитель указал и время отправления, и время прибытия, **когда** он создаёт поездку, **тогда** сервис сохраняет оба значения.
- **Дано** водитель не завершил и не отменил поездку вручную, **когда** проходит два часа после указанного времени отправления или прибытия, **тогда** сервис автоматически завершает поездку.

## Сценарий 2. Поиск поездки

**Цель:** пассажир находит подходящую активную поездку.

**Участник:** авторизованный пользователь в роли пассажира.

**Основной поток:**

1. Пассажир открывает список активных поездок.
2. Сервис показывает доступные поездки.
3. Пассажир при необходимости задаёт фильтры: точка отправления, точка назначения и время.
4. Сервис показывает поездки, соответствующие заданным фильтрам.
5. Пассажир открывает карточку нужной поездки и видит маршрут, время, цену и оставшееся число мест.

**Критерии приёмки:**

- **Дано** в системе есть активные поездки, **когда** пассажир открывает список без фильтров, **тогда** он видит все активные поездки.
- **Дано** пассажир задал один или несколько фильтров, **когда** сервис обновляет список, **тогда** отображаются только поездки, соответствующие всем заданным фильтрам.
- **Дано** поездка отменена или завершена, **когда** пассажир открывает список активных поездок, **тогда** эта поездка не отображается.

## Сценарий 3. Бронирование мест

**Цель:** пассажир автоматически резервирует одно или несколько свободных мест в чужой поездке.

**Участник:** авторизованный пользователь в роли пассажира.

**Основной поток:**

1. Пассажир открывает незанятую активную поездку.
2. Пассажир указывает количество занимаемых мест.
3. Если мест больше одного, пассажир ставит пометку «бронирую другому».
4. Клиент отправляет запрос на бронирование с ключом идемпотентности.
5. API создаёт `BookingJob` в состоянии `Created` и передаёт его через `Dispatcher` в `BookingTool`.
6. `BookingTool` проверяет поездку и доступность мест, атомарно резервирует места и возвращает результат.
7. Сервис переводит `BookingJob` в состояние `Confirmed`, создаёт бронь и показывает её пассажиру и водителю.

**Критерии приёмки:**

- **Дано** поездка активна и имеет достаточно мест, **когда** пассажир бронирует указанное число мест, **тогда** сервис создаёт подтверждённую бронь и уменьшает число свободных мест на это число.
- **Дано** пассажир бронирует больше одного места и установил пометку «бронирую другому», **когда** мест достаточно, **тогда** сервис подтверждает бронь без запроса данных о попутчиках.
- **Дано** клиент повторяет запрос с тем же ключом идемпотентности, **когда** первый запрос уже обработан, **тогда** сервис возвращает результат первой операции и не создаёт вторую бронь.
- **Дано** пользователь является водителем выбранной поездки, **когда** он пытается забронировать в ней место, **тогда** сервис отклоняет запрос с ошибкой `SELF_BOOKING`.

## Сценарий 4. Отмена брони или поездки

**Цель:** участник отменяет бронь либо поездку, а сервис корректно освобождает места и обновляет статусы.

**Участники:** пассажир и водитель.

**Основной поток:**

1. Пассажир открывает свою подтверждённую бронь и выбирает отмену, либо водитель открывает свою поездку.
2. Водитель выбирает отмену брони конкретного пассажира или отмену всей поездки.
3. Сервис проверяет право пользователя на операцию.
4. При отмене отдельной брони сервис освобождает все места этой брони и меняет состояние связанного `BookingJob`.
5. При отмене поездки сервис отменяет все связанные подтверждённые брони и завершает жизненный цикл каждой из них.
6. Сервис отображает участникам актуальные статусы.

**Критерии приёмки:**

- **Дано** пассажир владеет подтверждённой бронью, **когда** он отменяет её, **тогда** бронь получает состояние `CancelledByPassenger`, а все занятые ею места снова доступны.
- **Дано** водитель владеет поездкой, **когда** он отменяет бронь пассажира, **тогда** бронь получает состояние `CancelledByDriver`, а места освобождаются.
- **Дано** водитель отменяет поездку, **когда** в ней есть подтверждённые брони, **тогда** поездка отменяется, а каждая бронь получает состояние `CancelledBecauseTripCancelled`.
- **Дано** пользователь не является владельцем брони или поездки, **когда** он пытается её отменить, **тогда** сервис возвращает ошибку `FORBIDDEN` и не меняет данные.

## Сценарий 5. Ошибка: недостаточно свободных мест

**Цель:** сервис не допускает переполнения поездки.

**Участник:** авторизованный пассажир.

**Основной поток:**

1. Пассажир выбирает активную чужую поездку.
2. Пассажир запрашивает количество мест, превышающее остаток.
3. API создаёт `BookingJob` и передаёт его в `BookingTool`.
4. `BookingTool` в транзакции обнаруживает, что свободных мест недостаточно.
5. Сервис переводит `BookingJob` в состояние `Failed`, не создаёт бронь и не меняет число свободных мест.

**Критерии приёмки:**

- **Дано** в поездке осталось два свободных места, **когда** пассажир пытается забронировать три места, **тогда** сервис возвращает ошибку `INSUFFICIENT_SEATS`, не создаёт бронь и оставляет два свободных места.
- **Дано** два пассажира одновременно пытаются забронировать последние места, **когда** операции обрабатываются параллельно, **тогда** количество подтверждённых мест не превышает вместимость поездки, а лишняя операция завершается ошибкой `INSUFFICIENT_SEATS`.
- **Дано** пассажир указывает ноль или отрицательное число мест, **когда** он отправляет запрос, **тогда** сервис возвращает ошибку `INVALID_SEAT_COUNT`.

## Сценарий 6. Ошибка: некорректные данные поездки или локации

**Цель:** сервис не создаёт поездку по некорректным данным и корректно обрабатывает сбой внешнего API.

**Участник:** авторизованный водитель.

**Основной поток:**

1. Водитель открывает форму создания поездки.
2. Водитель вводит или выбирает точки через API Яндекс Карт.
3. Сервис получает ответ внешнего API и проверяет параметры формы.
4. Если внешнее API недоступно, вернуло некорректный ответ или пользователь указал недопустимые данные, сервис не создаёт поездку и возвращает машиночитаемую ошибку.

**Критерии приёмки:**

- **Дано** точки отправления и назначения совпадают, **когда** водитель создаёт поездку, **тогда** сервис возвращает ошибку `SAME_LOCATIONS`.
- **Дано** водитель не указал ни время отправления, ни время прибытия, **когда** он создаёт поездку, **тогда** сервис возвращает ошибку `TIME_REQUIRED`.
- **Дано** водитель указал ноль или отрицательное количество мест либо отрицательную цену, **когда** он создаёт поездку, **тогда** сервис возвращает соответственно `INVALID_SEAT_COUNT` или `INVALID_PRICE`.
- **Дано** API Яндекс Карт недоступно, превышен timeout или оно вернуло данные без координат, **когда** пользователь ищет или выбирает локацию, **тогда** адаптер выполняет ограниченные повторы и после неудачи возвращает ошибку `LOCATION_PROVIDER_UNAVAILABLE`; поездка не создаётся.

## Жизненный цикл BookingJob

| Состояние | Смысл | Разрешённые переходы |
| --- | --- | --- |
| `Created` | Запрос на бронирование принят API и ожидает обработки. | `Confirmed`, `Failed` |
| `Confirmed` | Места атомарно зарезервированы, бронь активна. | `Completed`, `CancelledByPassenger`, `CancelledByDriver`, `CancelledBecauseTripCancelled` |
| `Completed` | Поездка завершена, бронь закрыта. | Нет — конечное состояние. |
| `CancelledByPassenger` | Бронь отменил пассажир. | Нет — конечное состояние. |
| `CancelledByDriver` | Бронь отменил водитель. | Нет — конечное состояние. |
| `CancelledBecauseTripCancelled` | Водитель отменил всю поездку. | Нет — конечное состояние. |
| `Failed` | Бронирование не выполнено из-за проверки данных, отсутствия мест или состояния поездки. | Нет — конечное состояние. |

Переходы, отсутствующие в таблице, запрещены. Например, нельзя подтвердить отменённую бронь или отменить завершённую.

## Что предложил ИИ

**Промпт:**

> Мы проектируем учебный сервис NVKDrive на ASP.NET Core. Пассажир автоматически бронирует одно или несколько мест в чужой поездке; при брони нескольких мест нужна пометка «бронирую другому». Найди способы сломать этот основной сценарий бронирования, учитывая параллельные запросы, отмену поездки, повторные HTTP-запросы и внешнее API локаций. Для каждого предложи техническую защиту.

| Предложение ИИ | Решение | Почему |
| --- | --- | --- |
| Два пассажира одновременно бронируют последние места. | Принято. | Резервирование мест выполняется атомарно в транзакции БД; вместимость не может быть превышена. |
| Клиент повторно отправляет запрос после сетевой ошибки и создаёт дубликат брони. | Принято. | `POST` бронирования использует ключ идемпотентности и повторяет предыдущий результат. |
| Водитель отменяет поездку одновременно с бронированием. | Принято. | Обработчик проверяет активность поездки в той же транзакции; бронь не уменьшает места отменённой поездки. |
| Пассажир запрашивает несколько мест, но свободных мест меньше, чем запрошено. | Принято. | Создаётся `Failed`-Job с ошибкой `INSUFFICIENT_SEATS`, без частичного резервирования. |
| Пассажир бронирует несколько мест без пометки «бронирую другому». | Принято. | API валидирует флаг и возвращает ошибку до создания брони. |
| API Яндекс Карт возвращает пустой или некорректный ответ. | Принято. | Адаптер проверяет ответ, использует timeout и ограниченные повторы; пользователь получает единую ошибку. |
