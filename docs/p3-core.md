# Контракты ядра NVKDrive для практики 3

Целевая платформа — C# и `net10.0`. Источник правил переходов — диаграмма в [архитектуре](architecture.md) и [ADR-0002](0002-synchronous-booking-jobs.md). Граница этапа проходит перед HTTP, PostgreSQL, идемпотентностью HTTP, планировщиком и интеграцией с Яндекс Картами.

## Компоненты

- `BookingJob` владеет статусом и проверяет каждую команду перехода. Публичный статус доступен только для чтения. Захват записывает идентификатор обработчика, токен и срок lease. Подтверждение и фиксация ошибки требуют действующего lease и совпадающего токена. При `now >= leaseExpiresAt` отдельная команда закрывает обработку с `PROCESSING_INTERRUPTED`. Терминальные статусы сохраняются при последующих командах. Коды отказов берутся из архитектуры.
- Общие типы `ITool<TCommand, TResult>`, `ToolContext`, `ToolResult<TResult>`, `ToolError` и типизированные команды и результаты сохраняют форму из [контракта Tool](tool_contract.md). `ToolContext` содержит только `OperationId`, `UserId`, `JobId` и `LeaseToken`.
- Registry разрешает Tool по имени и проверяет типы команды и результата. Имена операций — `booking` и `trip-completion`. Неизвестное имя возвращает `UNKNOWN_OPERATION` до захвата Job. Дубликат имени — ошибка конфигурации.
- Dispatcher имеет маршрут с захватом Job для создания брони и маршрут без захвата для отмены отдельной брони и завершения поездки. Оба используют общий Registry. Новый Tool подключается регистрацией. Отмена и завершение меняют связанные подтверждённые Job через доменные команды.
- Tool проверяет бизнес-правила и возвращает `Failure` для ожидаемых ошибок. Для отсутствующего обязательного значения, пустого обязательного идентификатора или неизвестного значения enum применяется `INVALID_PARAMETER` с именем поля. Специальные коды бизнес-ошибок сохраняются. Исключение Tool преобразуется в `TOOL_EXECUTION_FAILED` без текста исходного исключения.
- Домен получает время явно как `DateTimeOffset`. Dispatcher и инструменты используют `TimeProvider`. Длительность lease задаётся конфигурацией Dispatcher.
- `BookingTool` создаёт бронь и отменяет отдельную бронь. `TripCompletionTool` завершает поездку и подтверждённые брони. При автоматическом завершении используется `(ArrivalTime ?? DepartureTime) + 2 часа`. Для отмены всей поездки на этом этапе предусмотрены переход `CancelledBecauseTripCancelled` и тест.

## Обработка и атомарность

1. Dispatcher разрешает регистрацию, затем для создания брони атомарно сохраняет `Processing` с lease. Конкурентный вызов видит уже захваченный Job и получает отказ до запуска Tool.
2. На вызов создаётся сессия через интерфейс хранилища. Tool получает её как зависимость. Сессия держит изменения изолированно до фиксации. Операции над одной поездкой сериализуются.
3. При успешном создании Dispatcher в одной атомарной операции проверяет актуальность lease и записывает бронь, остаток мест и `Confirmed`. При отмене отдельной брони и завершении поездки все связанные изменения также фиксируются вместе.
4. При бизнес-ошибке или исключении изменения сессии отбрасываются, а Job с действующим lease переходит в `Failed`. Если lease истёк, применяется `PROCESSING_INTERRUPTED`. Запоздалый результат не фиксирует изменения.
5. При отмене вызова через `CancellationToken` изменения сессии отбрасываются, вызывающему передаётся отмена. Уже захваченный Job закрывается по истечении lease при следующем обращении.

## Приёмка и остановка

- Сборка и тесты запускаются одной командой из README. Ядро работает с реализацией хранилища в памяти и не импортирует веб-фреймворк или драйвер БД.
- Сквозной тест проверяет `Created → Processing → Confirmed → Completed`, создание брони и остаток мест. Для З1–З6 предусмотрено по отдельному тесту. З2 воспроизводится сохранённым `Processing` и управляемым временем.
- Тестируются неизвестная операция, невалидные параметры с полем, бизнес-ошибка и исключение Tool, подключение нового Tool, конкурентное бронирование последних мест, откат при истечении lease и отмене вызова, освобождение мест ровно один раз.
- Агент останавливается сразу, если для продолжения требуется новое бизнес-правило, изменение согласованного контракта или расширение объёма. При воспроизводимом техническом сбое допускается одна обоснованная попытка исправления. При повторном сбое агент передаёт команду проверки, фактический результат, недостигнутый критерий и список изменённых файлов. Проверки остаются включёнными.
