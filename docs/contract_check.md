# Проверка контракта колодой

## Карты К1–К10

| Карта | Ответ контракта |
| --- | --- |
| **К1 Двойной клик** | Клиент передаёт `Idempotency-Key`. Два запроса одного пользователя с одинаковыми ключом и телом создают один Job. Повтор возвращает `200` и прежний `jobId`; Tool повторно не запускается — [`POST /jobs`](api/openapi.yaml). |
| **К2 Ответ потерялся** | Клиент повторяет `POST /jobs` с прежним `Idempotency-Key` и получает существующий Job либо запрашивает его через `GET /jobs/{jobId}`. Новая операция не создаётся — [`POST /jobs` и `GET /jobs/{jobId}`](api/openapi.yaml). |
| **К3 Неизвестная операция** | API возвращает `400 INVALID_OPERATION` с полем `operation`. Job не создаётся, поскольку формат команды проверяется до её создания — [`POST /jobs`](api/openapi.yaml), схема `ErrorResponse`. |
| **К4 Кривые параметры** | Отсутствующее поле, неверный тип или недопустимое значение дают `400 VALIDATION_ERROR`. Поле `field` в теле ошибки указывает ошибочный параметр. Job не создаётся — [`ErrorResponse`](api/openapi.yaml) и [распределение проверок](tool-contract.md#распределение-проверок). |
| **К5 Воскрешение** | Перезапуск завершённого Job запрещён: система возвращает `409 JOB_ALREADY_TERMINAL`. Повтор с прежним ключом возвращает прежний результат. Новая попытка после `Failed` требует нового `Idempotency-Key` и создаёт новый Job — [диаграмма состояний](architecture.md#диаграмма-состояний-bookingjob) и [ADR-0002](adr/0002-synchronous-booking-jobs.md). |
| **К6 Отмена** | Отмена Job в состоянии `Processing` не поддерживается: операция короткая и выполняется одной транзакцией. Запрос отмены получает `409 JOB_ALREADY_PROCESSING`; частичный результат не фиксируется. После `Confirmed` пассажир или водитель может отменить бронь отдельной командой — [`POST /jobs/{jobId}/cancel`](api/openapi.yaml), [`BookingTool`](tool-contract.md#bookingtool) и [ADR-0002](adr/0002-synchronous-booking-jobs.md). |
| **К7 Огромный вход** | HTTP API ограничивает тело запроса; превышение лимита возвращает `413 PAYLOAD_TOO_LARGE`. Длины строк и диапазоны числовых полей заданы в OpenAPI; нарушение ограничения возвращает `400 VALIDATION_ERROR` с именем поля. Job не создаётся — [схемы запросов и `ErrorResponse`](api/openapi.yaml). |
| **К8 Чужой или несуществующий id** | Для отсутствующего и принадлежащего другому пользователю Job возвращается одинаковый ответ `404 JOB_NOT_FOUND`. Содержимое чужого Job не раскрывается — [`GET /jobs/{jobId}`](api/openapi.yaml). |
| **К9 Перезапуск сервера** | Job и его `lease` хранятся в PostgreSQL. После перезапуска Job временно остаётся `Processing`; после истечения `lease` при следующем чтении он атомарно переводится в `Failed` с кодом `PROCESSING_INTERRUPTED`. Автоматического повторного запуска нет — [диаграмма состояний](architecture.md#диаграмма-состояний-bookingjob) и [ADR-0002](adr/0002-synchronous-booking-jobs.md). |
| **К10 Внешний сервис** | `BookingJob` не обращается к API Яндекс Карт, поэтому его обработка от этого сервиса не зависит. При создании поездки адаптер использует timeout, ограниченные повторы и проверяет структуру ответа. После неудачи API возвращает `502 LOCATION_PROVIDER_UNAVAILABLE`, а поездка не создаётся — [диаграмма компонентов](architecture.md#диаграмма-компонентов) и [`POST /trips`](api/openapi.yaml). |

## Что предложил ИИ

### Промпт

> Ты выступаешь атакующим при проверке контракта сервиса NVKDrive.
>
> NVKDrive — сервис совместных поездок. Водитель создаёт, завершает и отменяет поездки. Пассажир бронирует одно или несколько мест и может отменить бронь. Основная единица обработки бронирования — `BookingJob`.
>
> Жизненный цикл Job: `Created → Processing → Confirmed → Completed`. Из `Processing` возможен переход в `Failed`. Из `Confirmed` возможны переходы в `CancelledByPassenger`, `CancelledByDriver` и `CancelledBecauseTripCancelled`. `Completed`, `Failed` и состояния отмены являются конечными.
>
> Создание Job идемпотентно по сочетанию `userId + Idempotency-Key`. Job выполняется синхронно и не перезапускается автоматически после ошибки. Создание брони, уменьшение числа свободных мест и подтверждение Job выполняются в одной транзакции PostgreSQL. Для работы с локациями используется API Яндекс Карт.
>
> Уже проверены ситуации колоды: повтор одного запроса; потеря ответа; неизвестная операция; некорректные параметры; повторный запуск завершённого Job; отмена во время выполнения; слишком большой вход; чужой или несуществующий идентификатор; перезапуск сервера; timeout или некорректный ответ внешнего сервиса.
>
> Изучи контракт OpenAPI, контракт Tool, диаграмму состояний и ADR. Сыграй атакующего и найди ровно три новые ситуации, на которые контракт не отвечает однозначно. Не повторяй ситуации К1–К10. Ищи гонки между разными операциями, неоднозначные правила и граничные случаи.
>
> Для каждой находки укажи последовательность действий, что может сломаться, чего не хватает в контракте и какое правило или изменение контракта устранит проблему. Не предлагай функции, не относящиеся к MVP: платежи, рейтинги, чат, уведомления и проверку личности.

### Результаты проверки

| Находка ИИ | Решение | Что изменили и почему |
| --- | --- | --- |
| **Одновременные бронирование и отмена поездки.** Пассажир бронирует место в тот момент, когда водитель отменяет поездку. Без правила порядка операций может появиться подтверждённая бронь отменённой поездки. | Принято. | В [контракте BookingTool](tool-contract.md#bookingtool) закрепили, что проверка состояния поездки, резервирование мест и создание брони выполняются в одной транзакции с блокировкой поездки. Отмена использует ту же блокировку. Если первой фиксируется отмена, бронирование получает `TRIP_NOT_ACTIVE`. Если первой фиксируется бронь, последующая отмена переводит её в `CancelledBecauseTripCancelled`. |
| **Повтор с тем же ключом после очистки данных идемпотентности.** Клиент повторяет старый запрос, а запись о ключе уже удалена. Система может создать вторую бронь. | Принято. | В [`POST /jobs`](api/openapi.yaml) закрепили правило: запись `userId + Idempotency-Key`, хеш запроса и сохранённый результат хранятся не меньше соответствующего Job. В MVP записи идемпотентности автоматически не удаляются, поэтому повтор старого запроса возвращает первоначальный Job. |
| **Неоднозначное время автоматического завершения.** У поездки указаны и время отправления, и время прибытия, но контракт не определяет, от какого времени отсчитывать два часа. | Принято. | В [контракте TripCompletionTool](tool-contract.md#tripcompletiontool) закрепили: если указано время прибытия, автоматическое завершение выполняется через два часа после него; время отправления используется только при отсутствии времени прибытия. Ранний запуск получает `COMPLETION_TIME_NOT_REACHED`. |
